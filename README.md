# Как подготовить качественный конспект по видео или аудио

**Цель:** получить конспект, который передаёт основные идеи, понятия и правила, а также практику применения, если она была в записи. По конспекту должно быть понятно, что утверждал автор, при каких условиях действует правило и как предлагается его применять.

Рабочая последовательность:

**Запись → две транскрипции → сверка и спорные места в diff → ручная проверка → полная выверенная транскрипция → ход развития мысли → итоговый конспект → проверка и, при необходимости, публикация.**

ИИ готовит тексты и выделяет вопросы. Человек проверяет смысловые сомнения по записи и утверждает результат. Совпадение двух распознаваний повышает уверенность, но само по себе не доказывает точность.

Код и инструкции доступны в [GitHub-репозитории](https://github.com/smarkin-repository/LabVideoTransription). После клонирования перейти в папку проекта и выполнить настройку среды ниже:

```bash
git clone https://github.com/smarkin-repository/LabVideoTransription.git
cd LabVideoTransription
```

Записи, транскрипции и результаты встреч хранятся локально в `input/` и `output/` и исключены из Git. Эти папки создаются по мере работы. Зависимости Python перечислены в [requirements.txt](requirements.txt), имя переменной для ключа — в [.env.example](.env.example); пример не содержит рабочего ключа.

## Настройка среды с нуля: Linux и macOS

Установку выполнить один раз на каждом компьютере. Ниже команды для терминала **Bash или zsh**. Пути в кавычках заменить на свои; команды проекта выполнять из его корня, где находятся `main.py` и `create_dialogue.py`.

**До создания `.venv` проверить, нет ли готового окружения.** Если проект уже работает на этом компьютере, повторную установку и создание окружения пропустить, перейти к проверке импортов. Если папка проекта перенесена с другого компьютера вместе с `.venv`, сначала переименовать чужую `.venv`, например в свободное имя `.venv.previous`, затем выполнять команды создания новой. Готовое окружение между Linux и macOS не переносить.

### Общие шаги: установить библиотеки и проверить скрипты

Находясь в корне проекта, выполнить:

```bash
.venv/bin/python -m pip install --upgrade pip
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m pip check
.venv/bin/python --version
```

Устанавливать библиотеки в `.venv`, без `sudo pip`. Окружение создаётся заново на каждом новом компьютере и использует установленный на нём Python. [Устройство виртуальных окружений Python](https://docs.python.org/3/library/venv.html).

Проверить импорты, которые нужны `main.py`, без отправки записи в сервис:

```bash
.venv/bin/python -c 'from assemblyai import Client, Settings; from assemblyai.prerecorded.v2 import Transcriber, TranscriptionConfig; from importlib.metadata import version; print("AssemblyAI:", version("assemblyai")); print("Импорты main.py: OK")'
.venv/bin/python create_dialogue.py --help
```

Ожидаемый результат: `pip check` сообщает `No broken requirements found`, проверка импортов выводит версию и `OK`, а конвертер — справку. У `main.py` флага `--help` нет: ему передаётся только путь к записи.

Во всех командах ниже используется явный путь `.venv/bin/python`, поэтому активировать окружение не обязательно. Если удобнее писать `python`, можно выполнить `source .venv/bin/activate`; для выхода — `deactivate`.

### Задать API-ключ AssemblyAI

Получить ключ в аккаунте AssemblyAI. В том же терминале, из которого будет запускаться `main.py`, ввести ключ без отображения на экране:

```bash
printf 'Введите API-ключ AssemblyAI: '
read -r -s ASSEMBLYAI_API_KEY
printf '\n'
export ASSEMBLYAI_API_KEY
```

После вставки ключа нажать Enter. Проверить наличие переменной, не выводя её значение:

```bash
.venv/bin/python -c 'import os; print("API-ключ задан" if os.environ.get("ASSEMBLYAI_API_KEY") else "API-ключ не задан")'
```

Ключ действует в текущем терминале и запускаемых из него процессах. В новом терминале ввод повторить. Активация `.venv` не задаёт ключ, а существующий `.env` скрипт автоматически не читает.

## Перед началом: сохранить источники и определить результат

Создать папку `output/<название встречи>/`. Сохранить исходную запись, выгрузку Zoom и результат второго сервиса. Исходные транскрипции оставить неизменными; работать с отдельной копией.

Кратко записать:

- название, дату встречи и известных участников;
- путь или ссылку на запись, её продолжительность, наличие обрезки или пауз;
- для кого готовится материал и зачем: вспомнить лекцию, разобраться в идеях, применять правила, выполнить домашнюю работу;
- желаемый формат и объём: конспект, связное изложение лекции, памятка или практические задания.

Если формат пока не выбран, начать с конспекта основных идей, правил и прозвучавшей практики. Ссылки на источник сохранить и при дальнейшей адаптации.

## 1. Получить две транскрипции и сверить их

### Первый источник — Zoom

Для облачной транскрипции нужны тариф Pro, Business, Education или Enterprise, облачная запись и включённая функция создания транскрипции. В веб-портале Zoom открыть настройки записи, включить **Cloud recording**, затем **Create audio transcript** в расширенных настройках облачной записи и сохранить изменения. Сделать это до встречи. Если настройка заблокирована администратором, её меняет администратор. [Настройка Zoom](https://support.zoom.com/hc/en/article?id=zm_kb&sysparm_article=KB0065911).

После обработки скачать запись и файл транскрипции `.vtt` с таймкодами из раздела **Recordings & Transcripts → Cloud recordings**. Проверить язык: для русскоязычной встречи выбрать русский; при необходимости воспользоваться **Change Language** для повторного распознавания. [Работа с транскрипцией Zoom](https://support.zoom.com/hc/en/article?id=zm_kb&sysparm_article=KB0064927).

Не подменять полную расшифровку автоматическим резюме встречи. Для этого процесса нужны сами реплики с таймкодами.

### Второй источник — AssemblyAI

В этом проекте используется **AssemblyAI** через [main.py](main.py). Сервис принимает файл записи и поддерживает автоматическое определение языка и разделение по говорящим. [Документация AssemblyAI](https://www.assemblyai.com/docs/pre-recorded-audio/getting-started/transcribe-an-audio-file).

Желательно передавать ту же запись, к которой относится Zoom-транскрипция. Если файлы отличаются, зафиксировать различия до сравнения.

Порядок запуска в текущем проекте:

1. Подготовить доступ к AssemblyAI и API-ключ.
2. В том же терминале задать переменную окружения `ASSEMBLYAI_API_KEY` по командам раздела «Настройка среды». Наличие файла `.env` недостаточно: `main.py` не загружает его автоматически. Ключ не включать в документы и запросы к ИИ.
3. Создать новую папку встречи и разместить в ней копию записи с именем `input` и исходным расширением. Например, для MP4:

```bash
mkdir -p "output/Название встречи"
cp "/путь/к/записи.mp4" "output/Название встречи/input.mp4"
.venv/bin/python main.py "output/Название встречи/input.mp4"
```

Заменить примерные пути на свои. Команды выполнять из корня проекта, используя существующее окружение `.venv` с установленными зависимостями. Для повторного распознавания сначала сохранить предыдущие результаты в архив: скрипт записывает файлы с теми же именами.

Текущий `main.py` использует EU endpoint, автоматическое определение языка и метки говорящих. Рядом с записью он сохраняет:

- `input.json` — текст, реплики, таймкоды в миллисекундах и данные распознавания;
- `input.speakers.json` — соответствие меток говорящих именам и ролям.

Имена в `input.speakers.json` заполнять только после проверки. Метка `A` в одном источнике не обязательно обозначает того же человека, что `A` в другом. Голоса во вставленном видео тоже могут получить метки участников.

Для чтения и сверки получить диалог:

```bash
.venv/bin/python create_dialogue.py "output/Название встречи/input.json" -o "output/Название встречи/dialogue.md"
```

Конвертер программно переносит начало и конец каждой реплики из `start_ms` и `end_ms`, сохраняя миллисекунды, и добавляет ID:

```text
[U000001 | 00:00:00.000–00:00:01.234] A:Иван: Текст реплики.
```

ID — номер позиции реплики в конкретном исходном JSON. При повторной конвертации того же JSON он сохраняется; при дальнейшей редактуре текста его не перенумеровывать. У другого распознавания свои ID: при объединении указывать источник, например `AssemblyAI:U000001`. Режим `--short` убирает только метку говорящего `A`, оставляя имя, ID и время.

Отсутствующее время обозначается `??:??:??.???`; конвертер его не угадывает. Некорректные значения времени и интервалы с концом раньше начала вызывают ошибку до записи результата. Исходный `input.json` сохранять для проверки; ИИ не должен заново вычислять таймкоды или восстанавливать их по длине текста.

### Сверить время, полноту и смысл

Сначала сопоставить одинаковые фразы в начале, середине и конце. За основу времени удобно взять положение в сохранённой записи. Если в транскрипции отсчёт другой, записать соответствие шкал. Например: «таймкод TXT = время записи + 00:01:07». Это пример; для каждой встречи смещение проверяется заново.

При вырезанных фрагментах или остановках записи одного смещения может быть недостаточно: потребуется соответствие по отдельным участкам. Не переносить таймкоды механически через такой разрыв.

Затем прочитать оба текста целиком и собрать одну рабочую транскрипцию:

- выбрать основной текст по качеству и полноте; уже подтверждённые человеком правки сохранить;
- проверить, нет ли пропусков начала, конца или целых обсуждений; уникальные фрагменты одного источника не удалять только из-за отсутствия во втором;
- исправить явные опечатки и однозначные ошибки; для корректуры готового текста использовать [навык `transcript-proofread`](.agents/skills/transcript-proofread/SKILL.md);
- отдельно выделить существенные расхождения: отрицания, термины, числа, условия, причинные связи, автора высказывания, «кто делает» и «кому адресовано»;
- не нагружать ручную проверку разницей в пунктуации, разбивке фраз и словами-паразитами, если она не меняет смысл.

У сервисов разная разбивка речи. Число строк или реплик между двумя распознаваниями не является проверкой полноты. Сверять нужно последовательность содержания и покрытие записи. Если оба источника дают сомнительную фразу, её тоже нужно отметить, даже при совпадении текста.

Структурную проверку выполнять отдельно для двух операций. **После объединения** сверить собранный рабочий текст с обоими источниками: учтены ли уникальные фрагменты, сохранены ли порядок содержания и происхождение вставок, согласованы ли говорящие и шкалы времени. Сохранить копию этого текста до корректуры в `архив/`. **После корректуры** сравнить результат именно с этой копией: реплики, ID и таймкоды должны сохраниться; подтверждённые изменения времени или авторства фиксировать в журнале. Не требовать одинакового количества реплик у разных сервисов.

### Как оформлять спорное место

Сохранить рабочий текст в `01 — Транскрипция на проверку.md`. В нужной позиции поставить номер вопроса, ориентир в записи, соседний контекст и два варианта:

````markdown
### Q-007 · 00:42:10–00:42:28 по записи · Иван

Контекст: перед этим обсуждается, когда можно переходить к следующему действию.

```diff
- Zoom: Это нужно делать, если условие не выполнено.
+ AssemblyAI: Это не нужно делать, если условие не выполнено.
```

Вопрос: есть ли отрицание перед «нужно»?
Статус: требует прослушивания.
````

Это условный пример. **Знаки `−` и `+` обозначают источники, а не удаление и утверждённую замену.** Легенду указать в начале файла. До проверки ни один вариант не считать верным.

Для каждого вопроса нужен один конкретный предмет проверки. Если оба варианта повреждены, прямо написать об этом. Рядом сохранять достаточно исходных реплик, чтобы человек мог понять контекст. Полный список вопросов вести в `02 — Проверка спорных мест.md`: номер, таймкод, статус, ответ человека и основание. Сам diff достаточно хранить в рабочем тексте, не дублируя его в нескольких файлах.

**Результат этапа:** два сохранённых источника, единая рабочая транскрипция и короткий список значимых сомнений.

## 2. Человеку проверить спорные места

Открыть запись по указанному времени, прослушать фрагмент вместе с контекстом и зафиксировать ответ:

| Поле | Что записать |
|---|---|
| Номер | Например, Q-007 |
| Проверенный фрагмент | Время в записи |
| Итоговая формулировка | Что действительно удалось разобрать |
| Основание | Прослушивание записи, подтверждение говорящего или уточнение по памяти |
| Статус | Решено / частично уточнено / не удалось разобрать |

Уточнение по памяти не выдавать за проверку по аудио. Если слово осталось неразборчивым, сохранить понятную часть фразы и поставить `[неразборчиво]`. Не выбирать вариант только потому, что он звучит логичнее.

После ответа обновить рабочий текст и статус вопроса. Можно править самому или передать ИИ список ответов с номерами. Не выполнять массовую замену термина по всей встрече без проверки каждого контекста.

**Результат этапа:** ответы на смысловые вопросы и явно обозначенные остаточные неясности.

## 3. Зафиксировать полную выверенную транскрипцию

На основе проверенного рабочего текста создать `03 — Полная транскрипция.md`. Сохранить последовательность речи, границы реплик, говорящих и проверенные таймкоды. Не сокращать примеры, повторы или вопросы ради читабельности: сокращение относится к следующему этапу.

В начале указать статус, дату редакции, использованные источники, шкалу времени и границы проверки: например, «сверено по двум текстам; спорные места проверены по записи». Если всю запись не прослушивали, не писать, что выполнена полная аудиопроверка.

Готовность определять по содержанию, а не по имени файла:

- начало, основные части и конец записи учтены; известные пропуски обозначены;
- важные смысловые разногласия разрешены либо соответствующий фрагмент явно признан неустановленным;
- в утверждённом тексте нет невыбранных diff-вариантов;
- несущественные неясности помечены и не будут использоваться как установленные сведения;
- реплики не потерялись и не переставились при объединении и корректуре.

Если неясность касается центрального тезиса или шага практики, вернуться к проверке либо явно указать, что эту часть восстановить нельзя. Не закрывать пробел догадкой.

Исходники, diff и ответы сохранить в рабочих файлах или архиве. В дальнейшем использовать `03 — Полная транскрипция.md` как утверждённый источник. Исправление смысла сначала вносить в него с записью в журнале, затем обновлять конспект и производные материалы.

**Результат этапа:** полная транскрипция с понятным статусом и историей существенных правок.

## 4. Применить навык и получить конспект

Использовать [навык `conspect`](.agents/skills/conspect/SKILL.md), передав **полную утверждённую транскрипцию**, цель и требования к результату. Навык должен прочитать весь доступный источник. Для длинной встречи читать его последовательными частями, затем собирать общий текст с проверкой связей и повторов.

Навык работает в три волны: подготовленная транскрипция, ход развития мысли, итоговый конспект. Уже выверенную транскрипцию повторно очищать не требуется. На её основе навык создаёт два отдельных документа: `04 — Ход развития мысли.md` и `<название встречи> - конспект.md`.

Итоговый конспект — связное объяснение основных идей, понятий, правил, ключевых вопросов и имеющейся практики. «Лекция» обозначает стиль последовательного объяснения простым языком. Сохранять рассуждения, которые раскрывают ключевые понятия и связывают их между собой; убирать отступления и повторы, не добавляющие смысла. Краткость — следствие аккуратной работы с информацией, а не самостоятельная цель. Образы, метафоры и значимые описания телесных ощущений сохранять с необходимым контекстом, когда они помогают понять идею или её применение.

Шаблон запроса:

```text
Используй $conspect.
Источник: output/<название встречи>/03 — Полная транскрипция.md.
Прочитай источник целиком. Он уже выверен, повторная очистка не нужна.
Сохрани в output/<название встречи>/ два документа:
1. 04 — Ход развития мысли.md — постановка вопросов, на что обращали
   внимание участники, как уточнялись понятия и формулировались идеи.
2. <название встречи> - конспект.md — связное объяснение основных идей,
   понятий, правил, ключевых вопросов и практики, если она обсуждалась.

Пиши простым языком. Сохрани рассуждения, раскрывающие ключевые понятия
и связи между ними; убери отступления и повторы без нового смысла.
Краткость не является самостоятельной целью. Сохрани образы и метафоры,
которые помогают понять идею, в необходимом для этого объёме.
Удели особое внимание описаниям телесных ощущений и их связи с практикой
в пределах сказанного участниками.
Сохрани условия правил, оговорки, отрицания, авторство и таймкоды.
Не додумывай объяснения, шаги упражнений и домашнюю работу.
Если практики нет, кратко укажи это. Пересказ не оформляй как цитату.
```

Для каждой важной идеи читатель должен понимать её смысл, ограничения и основание в записи. Если автор перечислил только часть действий или критериев, эту неполноту сохранить.

**Результат этапа:** документ о ходе развития мысли и отдельный итоговый конспект, проверяемые по полной транскрипции.

## 5. Отредактировать итоговый конспект под задачу

Доработать итоговый файл **`<название встречи> - конспект.md`**. Например: `Жизненные программы - конспект.md`. Подставить название встречи, сохранив разделитель ` - `. «Материал для публикации» — общее обозначение готового результата, отдельный файл с таким названием не требуется.

Сохранить предыдущую редакцию в архиве, если она уже была утверждена. Документ о ходе развития мысли оставить отдельно. Дополнительные форматы создавать, если они нужны для конкретной задачи.

| Задача читателя | Подходящий результат |
|---|---|
| Быстро вспомнить содержание | Короткий конспект: идеи, правила, важные примеры |
| Последовательно разобраться в теме | Связное изложение лекции с понятиями и объяснениями |
| Применять материал | Памятка с условиями и действиями, которые предложил автор |
| Выполнить практику | Отдельный раздел с реально данными заданиями и разбором примеров |

При адаптации можно менять порядок разделов, сокращать повторы, улучшать навигацию и выносить примеры в отдельный файл. Каждый содержательный пункт сверять с полной транскрипцией, особенно после сокращений.

Различать три вещи:

- **Практика автора:** задание, упражнение или способ действий, действительно предложенный в записи.
- **Пример из встречи:** иллюстрация мысли; сама по себе она ещё не является домашней работой.
- **Редакторское упражнение:** новое задание на основе материала. Добавлять его только по отдельному запросу и явно подписывать авторство редактора.

Каждый абзац должен помогать раскрыть идею, понятие, правило, вопрос, связь понятий или применение. Сохранять необходимые для понимания рассуждения, образы, метафоры и телесные ориентиры. Убирать лишние рассуждения и повторы, а не добиваться меньшего объёма самого по себе. Сохранять атрибуцию и обозначать редакционное изложение, если это не дословный текст; новые объяснения и рекомендации не приписывать автору.

Шаблон запроса для адаптации:

```text
Отредактируй <название встречи> - конспект.md для [аудитория и задача],
с учётом [пожелания к объёму, если заданы]. Проверяй содержание по 03 — Полная транскрипция.md
и используй 04 — Ход развития мысли.md для контекста.
Раскрой основные идеи, правила, вопросы, условия и ограничения.
Сохрани рассуждения, объясняющие ключевые понятия и связи между ними,
значимые образы, метафоры и телесные ощущения с необходимым контекстом.
Убирай только то, что не добавляет смысла; краткость не является целью.
Практику включай только в том объёме, в котором она дана в источнике.
Сохрани возможность перейти от важных положений к таймкодам.
Неразрешённые фрагменты не используй как установленные сведения.
Сохрани предыдущую утверждённую редакцию в архиве и обнови итоговый
файл <название встречи> - конспект.md. Документ о ходе развития мысли сохрани.
```

**Результат этапа:** материал под выбранную задачу, сверенный с источником.

## 6. Проверить итоговый конспект и при необходимости опубликовать

Перед завершением пройти короткую проверку:

- [ ] Основные идеи и правила встречи отражены; сокращения не изменили смысл.
- [ ] У существенных положений есть проверяемый ориентир в источнике.
- [ ] Сохранены условия, исключения, отрицания и авторство утверждений.
- [ ] Практика соответствует записи; отсутствующие шаги не дописаны.
- [ ] Изложение раскрывает основные идеи, правила и вопросы; сохранены рассуждения, объясняющие понятия и связи между ними, значимые образы, метафоры и телесные ощущения. Объём не сокращён ценой понимания.
- [ ] Вопросы, предположения и частные советы не превратились в факты и общие правила.
- [ ] В тексте нет невыбранных diff-вариантов и служебных пометок редактора; важные ограничения источника обозначены понятно читателю.
- [ ] Название, вступление и формат соответствуют содержанию: конспект, пересказ лекции или практические задания.
- [ ] Если текст перенесён на площадку, проверены заголовки, списки, таблицы и ссылки.

Готовый результат — файл `<название встречи> - конспект.md`. Если нужна публикация, использовать эту версию и сохранить в рабочей папке дату, площадку или ссылку на публикацию. При последующих существенных исправлениях обновлять источник, конспект и опубликованную версию согласованно.

## Организация файлов

Для новой встречи можно использовать такую структуру; существующие материалы переименовывать необязательно:

```text
output/<название встречи>/
├── input.mp4                         # запись или ссылка на неё
├── zoom.vtt                          # неизменённая выгрузка Zoom
├── input.json                        # исходный результат AssemblyAI
├── input.speakers.json                # проверяемые имена и роли
├── dialogue.md                       # диалог с ID реплик и таймкодами
├── 01 — Транскрипция на проверку.md   # полный рабочий текст с diff
├── 02 — Проверка спорных мест.md      # номера, ответы и статусы
├── 03 — Полная транскрипция.md        # утверждённый источник
├── 04 — Ход развития мысли.md
├── <название встречи> - конспект.md   # итоговый файл
├── Журнал.md                         # источники, шкала времени, правки, публикация
└── архив/                            # предыдущие версии и исходники до правок
```

Не создавать пустой список вопросов, если смысловых сомнений нет. Доработанный итог сохранять как `<название встречи> - конспект.md`; дополнительные файлы нужны только для отдельно выбранных форматов.

## Что упрощает процесс

1. **Одна утверждённая транскрипция.** Все производные материалы сверяются с ней; подтверждённые исправления не теряются между версиями.
2. **Ручная проверка по приоритету.** Сначала центральные идеи, термины, отрицания и шаги практики; затем менее значимые места.
3. **Стабильные номера вопросов.** Ответ «Q-007: …» проще однозначно внести и проверить, чем комментарий без привязки.
4. **Одно место для каждого изменения.** Diff хранится в рабочем тексте, решение — в списке вопросов, итог — в полной транскрипции.
5. **Чёткий статус на каждом этапе.** «Получено распознавание», «требует проверки», «транскрипция утверждена», «конспект проверен», «опубликовано» означают разные состояния.

Если Zoom-транскрипции нет, можно работать с AssemblyAI и записью. В журнале отметить, что второго текстового источника не было; сомнительные и ключевые места проверять по записи. При недоступной записи честно указать пределы текстовой сверки.

Технические команды описывают текущие [main.py](main.py) и [create_dialogue.py](create_dialogue.py). Сведения о сервисах проверены по документации 28 октября 2026 года; названия пунктов интерфейса и условия тарифов могут меняться.
